# Sketch-Prompted VLA — LIBERO rollout harness protocol

Aaron — 4 August 2026

Companion to the three suite `DATASHEET.md` files and `outputs/human_study/
HUMAN_STUDY.md`; canonical schema v1.0 (`SCHEMA.md`). This document records what
was actually measured while building the rollout harness and which resolution
was taken for each of the eight open issues in `prompt_libero_rollout_harness.md`,
then the condition matrix, the failure decomposition, how to run every stage, and
the current limitations.

The human-sketch collection tool is finished (`HUMAN_STUDY.md`) but has not been
sent to any annotator yet — `outputs/human_study/responses/` is empty. Every
number below is therefore from the **auto** sketches and the **text-only**
baseline over all 114 scenes; the `human:*` / `human_consensus` conditions are
implemented and wired into the harness (they are a `--conditions` string, not a
code path) but have nothing to score against yet.

## Issue 1 — the annotated initial state (blocker)

**Measured: 114/114 scenes reproduce at rung 1 (resample), attempt 1, 0.000px
residual. Zero scenes needed rung 2 (solve) or rung 3 (give up).**
`outputs/rollouts/init_state_capture_report.json` carries the per-scene detail;
`outputs/rollouts/nonreproducible.json` is empty.

This is a cleaner result than the ladder anticipated, and the reason is
mechanical rather than lucky: every builder's placement sampling is driven
exclusively by `build_bddl`'s own `np.random.default_rng(seed)` (an INDEPENDENT
generator), while the *env's* physical settle — the one that produced
`frame0.png` — consumes the single **global** `np.random.seed(seed)` call issued
immediately before it, and nothing else touches that global stream first. Replay
`np.random.seed(meta['seed'])`, construct the env, call `reset()` once: the very
first draw is bit-identical to the one that rendered `frame0.png`, verified by
re-projecting every `meta['all_pixels']` instance and comparing to the recorded
value (`scripts/capture_scene_init_states_wsl.py`, `TOL_PX = 1.0`, actual
residual 0.000px on every scene). Rungs 2 and 3 are implemented and exercised by
the script's own logic but were never needed on the real 114.

**Persistence.** `env.get_sim_state()` (`ControlEnv.get_sim_state` →
`sim.get_state().flatten()`) into each scene's `init_state.npz`
(`qpos`/`qvel`/`time`, `SCHEMA.md`); restored with `env.set_init_state(flat)`
(`ControlEnv.set_init_state` → `regenerate_obs_from_state` →
`sim.set_state_from_flattened` + `sim.forward()` + `check_success()` +
observable refresh). This install exposes `set_init_state`, so it is used in
preference to hand-rolling `sim.set_state()` + `sim.forward()` — it is the same
mechanism LIBERO's own eval harness uses via `init_files/*.pruned_init`.

**A second finding, not anticipated by the brief:** restoring `qpos`/`qvel` alone
is *physically* correct but not always *visually* correct. Some Goal-suite arenas
assign non-`qpos` visual state (material/texture) during `reset()`, drawn from
the same global `np.random` stream `frame0.png` was rendered against. Measured on
`goal/scene_0000`: `qpos` after `set_init_state` matched the capture-time `qpos`
bit-for-bit (`max abs diff = 0.0`) regardless, but the rendered frame differed by
up to 158/255 per channel when `set_init_state` was called without a preceding
seeded `reset()`, and matched exactly (`max diff = 0`) with one. **Every env
construction in this codebase (capture and rollout) therefore does
`np.random.seed(meta['seed'])` → construct → one throwaway `reset()` → *then*
`set_init_state`/`set_state`, on every suite, not only Goal** — the extra reset
is a no-op for Spatial/Object and required for some Goal scenes, and there is no
cheap way to tell the two apart in advance, so it is unconditional
(`rollout_sketch_wsl.py:open_scene_env`).

`frame0.png` was never regenerated by any of this — every check above compares
a *live render* against the existing PNG, never writes over it.

## Issue 2 — pixel → world deprojection

Implemented both rung 1 and rung 2 in `scripts/sketch_geometry.py` (rung 3,
nearest-instance snap, is deliberately **not** implemented on the sketch path —
see the module docstring and issue 2 in the brief).

Selected by `--deproject {plane,depth}` (default `plane`; `--depth-deproject`
is kept as a deprecated alias). Whichever is chosen applies to **every**
condition — the sketch-reading oracle and the firewalled text-only baseline
alike — via `resolve_z()` in `sketch_policies.py`. That symmetry is the point:
if only the sketch route got depth, "depth" would be a property of the
condition rather than of the method, and the headline gap would silently
absorb it.

- **Rung 1, support-plane intersection** (`plane`, the default; `SUPPORT_Z` in
  `sketch_policies.py`). One world-frame height per suite — spatial/goal table
  ≈0.92m, object floor-band visual-centre height ≈0.065m, measured directly off
  the pinned init states rather than guessed (a first guess of 0.03m for the
  Object suite undershot every grasp — see Limitations). **This constant is
  known to be wrong for part of the Object suite** — see "Object's flat
  groceries" below.
- **Rung 2, rendered depth** (`depth`; `depth_z_at_pixel` in
  `rollout_sketch_wsl.py`). Constructs the env with `camera_depths=[True]`,
  reads `camera_utils.get_real_depth_map` once per scene at the pinned initial
  state — the same frame the sketch was drawn on — and unprojects through the
  camera intrinsics/extrinsics at whatever pixel the policy chose. **Any run
  using this is an upper bound**: a real RGB-only policy has no depth channel.
  Both `run_config.json` and `summary.json` carry `upper_bound: true` and an
  `upper_bound_reason` string, and every `results.csv` row carries its own
  `deproject` / `z_pick` / `z_place`.

Both routes now resolve z **per pixel**, so pick and place get their own
height. The arrow head usually lands on a basket or plate at a different height
from the circled object; forcing one z on both was wrong even when that z was
right for the pick.

### Two row conventions in the depth path (a fixed bug)

`depth_z_at_pixel` originally applied `sketch_geometry`'s row flip to *both* the
depth-map lookup and the intrinsic back-projection. Only the second wants it:

- **Sampling** the depth map uses `row` **unflipped** — `get_real_depth_map`
  returns the corrected orientation, already matching `agentview_image` and
  therefore `pick_px`/`all_pixels`.
- **Back-projecting** through the intrinsics uses `(IMG_H-1) - row`, the raw
  OpenGL row the intrinsic matrix is defined against.

Flipping both sampled the mirrored row and silently read background: Spatial
`scene_0000`'s bowl came back at **z = −0.65 m** and Object's
`chocolate_pudding` at **−0.28 m**, both far-plane hits. It survived an earlier
spot-check because the first object checked, `plate_1`, sits at row 64 — whose
mirror is 63, essentially the same pixel. Verified against ground truth by
unprojecting each instance's recorded pixel and comparing to its live `vcenter`
z across all three suites; the corrected form now agrees to ~1 cm (Goal
`plate_1`: 0.9108 recovered vs 0.9108 true).

A single pixel is still fragile — at 128×128 a flat grocery box does not
reliably cover its own centre pixel — so the estimate is the **median world z
over a 3×3 patch** (`DEPTH_PATCH_K`), which rejects the occasional ray that
slips past the object into the background.

**Round-trip test** (`python scripts/sketch_geometry.py`, run before anything
else imported it, per the standing build order): deprojects every
`all_pixels`/`pick_px`/`place_px` entry from 30 real scenes (every 4th scene
across all three suites, boundary pixels excluded since clipping is lossy by
construction) at four candidate heights, reprojects, and asserts recovery within
1.0px. **Measured: worst offset (0.000, 0.000)px** — the deprojection is an exact
algebraic inverse of the forward projection the builders already use, so this
also validates issue 1's rung-2 pinning arithmetic (same routine).

## Issue 3 — how the sketch reaches the policy over time

Resolved as specified, no deviation:

- **Static prompt.** `Prompt` (`sketch_policies.py`) is built once at
  `SketchPolicy.reset()` and never touched again; `act(obs, t)` only ever
  receives the live `obs`.
- **Separate channel.** `Prompt.sketch_rgb` / `Prompt.symbolic_tokens` are never
  merged into `obs["agentview_image"]`. The live observation stays clean.
- **Both routes wired.** `--sketch-route {overlay,tokens}` selects which of
  `sketch_rgb` / `symbolic_tokens` is populated. **The two policies implemented
  here (`ScriptedSketchOracle`, `TextOnlyGuessPolicy`) only consume `tokens`** —
  they need numeric circle/arrow geometry to deproject, not image understanding.
  `overlay` is exercised structurally (the harness loads and hands over
  `sketch.png` correctly) but nothing in this repo reads it yet; that is the
  seam a learned (UniVLA) policy plugs into.

## Issue 4 — coordinate conventions

One module, `scripts/sketch_geometry.py`, numpy-only. Every function names its
pixel convention explicitly (`pixel_xy = (col, row)`, matching `pick_px` /
`symbolic_tokens`, never robosuite's native `(row, col)`) in its docstring, and
the round-trip test above is exactly the "fails loudly on a transposition" check
the brief asks for — a swapped axis or an un-applied row flip does not pass it.
No other file in this harness re-implements the projection math; both
`capture_scene_init_states_wsl.py` and `rollout_sketch_wsl.py` import it.

## Issue 5 — sustained success, and the permissive `In`

- **Sustained window.** `SUCCESS_WINDOW = 5` consecutive steps
  (`rollout_sketch_wsl.py`). `results.csv` records both `success_final` (last
  step only) and `success_sustained`, plus `first_success_step` — the step index
  the sustained window first opened.
- **Negative-oracle-style attribution at rollout time.** The reported
  success numbers (`success_final` / `success_sustained`) always come from
  `env.check_success()` on the scene's own BDDL-bound goal — never reimplemented.
  Alongside it, the harness computes an **approximate** post-hoc "which
  destination did the released object actually end up near" using xy proximity
  to every candidate destination's visual centre (`WRONG_DEST_APPROX_TH =
  0.08m`), reported as `nearest_destination` / `correct_destination`. This is a
  proximity proxy, not a re-derivation of LIBERO's true contact-solver
  `check_contact`/`check_ontop` logic (that would need a `data.contact` scan
  against every fixture, out of scope at this effort level) — it is a
  **failure-attribution aid**, never a substitute for `check_success()`, and is
  documented as approximate wherever it is reported. See Limitations.

## Issue 6 — the text-only baseline firewall

Structural, not disciplinary. `RestrictedPrompt` (`sketch_policies.py`) has no
`sketch_rgb`, `symbolic_tokens`, `target`, `destination`, `pick_px` or
`place_px` attribute anywhere on the class — a policy that tries
`prompt.pick_px` gets `AttributeError` at the first rollout, the same failure
mode `build_human_study_bundle.py`'s allow-list audit produces for its browser
payload. `RestrictedPrompt.candidate_pick_px` / `candidate_place_px` carry
**unlabelled**, harness-shuffled pixel centres — every same-category instance for
pick, every destination-typed instance for place (`candidate_pixels()` in
`rollout_sketch_wsl.py`) — the minimum a policy perceiving the raw RGB frame
would already know, never which one is correct. `TextOnlyGuessPolicy` picks
uniformly among them. On the 5 control-tier scenes per suite (single candidate),
this is necessarily 100%; the interesting number is the referential/directional/
both tiers, where it approximates 1/N — see the headline numbers below.

## Issue 7 — incomplete and incorrect human sketches

Not yet exercised against real data (no responses filed), but implemented and
smoke-tested against the mechanism:

- **Skipped / absent cells.** `load_sketch()` returns `ok=False` when a
  condition's `tokens.json` is missing for a `(annotator, suite, dir)` triple;
  the harness writes one `results.csv` row with `skipped=True,
  skip_reason=sketch_absent` and does **not** impute. `summary.json`'s rates are
  computed only over `skipped != True` rows, so an excluded cell never silently
  counts as a failure.
- **Sketch-following fidelity.** Every scored rollout records
  `sketch_referent_object` / `sketch_referent_destination` — the `all_pixels`
  instance nearest the sketch's circle centre / arrow head, the same
  nearest-candidate method `score_human_sketches.py` already uses — and
  `sketch_fidelity_object` / `sketch_fidelity_destination`, whether the policy's
  *actual* grasped instance / delivered-near destination matches what the
  sketch pointed to, independent of whether that was the scene's intended
  target. This is the "good policy given a bad prompt" measurement the brief
  asks for; it is columns in `results.csv`, not yet joined against
  `score_human_sketches.py`'s per-scene correctness labels (nothing to join
  against until real responses exist), which is the intended next step.

## Issue 8 — run-matrix cost and env leaks

- **One env per scene**, built in `open_scene_env`, reused across every
  condition × rollout for that scene, `init_state.npz` restored between them via
  `set_init_state` (never rebuilt per rollout).
- `env.close()` + `gc.collect()` between scenes (`rollout_sketch_wsl.py`'s
  per-scene `finally` block), exactly like the builders.
- **Resumable.** `results.csv` is appended to as the run proceeds;
  `--resume` reads it back into a `(suite, dir, condition, rollout_idx)` done-set
  and skips anything already present, so a run that dies partway restarts where
  it left off rather than from scene 0. A scene listed in
  `nonreproducible.json` gets one skip row (`skip_reason=nonreproducible:...`)
  instead of being simulated (moot on the real 114 — none are listed).
- **Scene-major order.** The roster is `(suite, dir)` outer, `(condition,
  rollout_idx)` inner, so a partial run yields complete rows for the scenes it
  reached rather than a partial column across every scene.

## Condition matrix

| condition | sketch source | policy that reads it |
|---|---|---|
| `text_only` | none — `RestrictedPrompt` | `text_guess` (`TextOnlyGuessPolicy`) |
| `auto` | `outputs/validation_set_<suite>/<dir>/` | `oracle` (`ScriptedSketchOracle`) |
| `human:<annotator>` | `outputs/human_study/rendered/<annotator>/validation_set_<suite>/<dir>/` | `oracle` |
| `human_consensus` | `outputs/human_study/rendered/consensus/validation_set_<suite>/<dir>/` | `oracle` |

`--policy` is one choice per invocation (a policy either reads `Prompt` or
`RestrictedPrompt`, not both), so comparing conditions is multiple invocations
sharing one `--run-id` with `--resume` — e.g. the run this document reports is
two calls: `--conditions text_only --policy text_guess` then `--conditions auto
--policy oracle --resume`, both `--scenes all`. A run whose `--conditions`
includes any `human:*` / `human_consensus` is automatically scoped to the
36-scene study subset (`outputs/human_study/scene_subset.json`); `text_only` +
`auto` alone cover all 114.

`NoOpPolicy` is the harness sanity check, not a condition-comparison arm: every
scene passed the builders' not-pre-solved gate, so it must score
`success_sustained=False` everywhere. Verified on one scene per suite
(`outputs/rollouts/smoke_noop/results.csv`) — 0/3.

## Failure decomposition (`results.csv` columns)

`grasped_any` / `lifted` use the **peak** height each instance reaches during the
episode, not its final one — a successfully placed object settles back near its
resting height, which would otherwise be indistinguishable from "never
grasped". `grasped_instance` / `correct_instance_grasped` identify which body
was actually lifted and whether it was the scene's `target`.
`nearest_destination` / `correct_destination` / `terminal_dist_xy` are the
approximate post-hoc destination attribution from issue 5.
`sketch_referent_object` / `sketch_referent_destination` /
`sketch_fidelity_object` / `sketch_fidelity_destination` are issue 7's fidelity
measurement. `grasp_success_flag` mirrors each scene's own `meta['grasp']
['grasp_success']` (6/38 Goal scenes carry `False` — SUITE_FACTS.md §3b.5) so
`summary.json` stratifies on it, per `README.md`. `deproject` / `z_pick` /
`z_place` record which rung produced each rollout's heights.

### The baseline seed was not reproducible (a fixed bug)

`TextOnlyGuessPolicy` is the only stochastic policy here — it picks uniformly
among the unlabelled candidate pixels. Its per-rollout seed was
`hash((suite, dir_, label, r_idx)) & 0xFFFFFFFF`, and **Python salts `hash()` of
`str` per process** (PYTHONHASHSEED randomisation), so every invocation drew a
different sample. Since a full run is two separate invocations, two runs of an
identical configuration disagreed: `full_run` scored `text_only` at 21.9% and an
otherwise byte-identical re-run scored it at 18.4% — moving the headline gap
from **+15.8pp to +19.3pp with no code change**. The `auto` half, driven by the
deterministic oracle, matched bit-for-bit across both, which is what isolated
the cause.

Now `stable_seed()` (blake2b over the joined key), which is stable across
processes, machines and Python versions. Two consequences:

- **`full_run`'s `text_only` column is one unreproducible draw** and its
  +15.8pp headline carries roughly ±3.5pp of pure RNG. It is kept for
  provenance but superseded by `full_run_plane` / `full_run_depth`.
- The baseline now runs **`--n-rollouts 3`** while the deterministic oracle
  stays at 1, so the denominator of the headline number is averaged over three
  draws per scene rather than one.

### `grasped_any` is not a targeting metric

**Never read `grasped_any` on its own.** It counts lifting *any* object, so a
baseline guessing uniformly among candidates can beat a policy that aims
correctly but misses — which is exactly what the Object suite produced under
the plane route: the oracle aimed truly at a flat grocery box and missed it by
~8 cm laterally, while the random baseline sometimes happened to land on a
graspable tall bottle and lifted that instead. Read as a targeting number this
inverts the result.

`grasped_correct` (`correct_instance_grasped` in the CSV — the target instance
and only it) is the column that answers "did the policy go for the right
thing". `summary.json` therefore reports the two together, per condition and
per condition×suite×tier, in `grasp_by_condition` /
`grasp_by_condition_suite_tier`, alongside `correct_destination`.

## How to run

```bash
conda activate libero
cd /mnt/c/Users/Admin/sketch_prompted_vla

# 0. the pure-numpy module, before anything imports it
python scripts/sketch_geometry.py

# 1. pin every scene's initial state (the 36 study-subset scenes first,
#    automatically, then the remaining 78)
python scripts/capture_scene_init_states_wsl.py --smoke        # 3-scene vertical slice
python scripts/capture_scene_init_states_wsl.py

# 2. vertical slice: one scene per suite, NoOp then oracle
python scripts/rollout_sketch_wsl.py --smoke --policy noop
python scripts/rollout_sketch_wsl.py --smoke --policy oracle

# 3. full run: text-only baseline, then the auto-sketch oracle, same run id.
#    --deproject applies to BOTH conditions; run it twice for the two rungs.
python scripts/rollout_sketch_wsl.py --conditions text_only --policy text_guess \
    --scenes all --deproject plane --n-rollouts 3 --run-id full_run_plane --resume
python scripts/rollout_sketch_wsl.py --conditions auto --policy oracle \
    --scenes all --deproject plane --run-id full_run_plane --resume

# same again with rendered depth -- an UPPER BOUND, stamped as such
python scripts/rollout_sketch_wsl.py --conditions text_only --policy text_guess \
    --scenes all --deproject depth --n-rollouts 3 --run-id full_run_depth --resume
python scripts/rollout_sketch_wsl.py --conditions auto --policy oracle \
    --scenes all --deproject depth --run-id full_run_depth --resume

# 4. side-by-side headline gap under both rungs
python scripts/compare_deprojection_runs.py --runs full_run_plane full_run_depth

# once human responses exist:
python scripts/score_human_sketches.py
python scripts/rollout_sketch_wsl.py --conditions human_consensus --policy oracle \
    --scenes subset --run-id full_run --resume
```

Every run writes `outputs/rollouts/<run_id>/{results.csv, summary.json,
run_config.json}`, optionally `videos/*.mp4` with `--video`.

## Headline numbers

Two runs, identical except for the deprojection rung, both over all 114 scenes,
`--max-steps 200`, `--sketch-route tokens`, deterministic `stable_seed()`:
`auto` (`oracle`) at `--n-rollouts 1` (the oracle is deterministic) and
`text_only` (`text_guess`) at `--n-rollouts 3` (it is not — see the seed bug
above). 456 scored rows each, 0 skipped.

| run | deprojection | `text_only` | `auto` | **gap** |
|---|---|---|---|---|
| `full_run_plane` | support plane (non-privileged) | 18.1% | 37.7% | **+19.6pp** |
| `full_run_depth` | rendered depth (**upper bound**) | 20.2% | 35.1% | **+14.9pp** |

**Quote +19.6pp.** The depth run is an upper bound — a real RGB-only policy has
no depth channel — and in any case it does *not* dominate; see below.

`full_run` (the earlier run, kept for provenance) reported +15.8pp. It is
superseded: its `text_only` column is a single unreproducible draw (see "The
baseline seed was not reproducible").

### Both deprojections, by suite

| suite | method | `auto` | `text_only` | gap | `grasped_correct` a/t | `grasped_any` a/t |
|---|---|---|---|---|---|---|
| spatial | plane | 71.1% | 27.2% | **+43.9** | 86.8 / 57.0 | 86.8 / 93.9 |
| spatial | depth | 68.4% | 29.8% | +38.6 | 81.6 / 54.4 | 81.6 / 88.6 |
| object | plane | 7.9% | 11.4% | **−3.5** | 15.8 / 18.4 | 15.8 / 31.6 |
| object | depth | 18.4% | 15.8% | **+2.6** | 36.8 / 30.7 | 36.8 / 57.9 |
| goal | plane | 34.2% | 15.8% | **+18.4** | 47.4 / 30.7 | 55.3 / 49.1 |
| goal | depth | 18.4% | 14.9% | +3.5 | 36.8 / 29.8 | 44.7 / 52.6 |

**Depth fixes Object and breaks Goal.** Object — the floor workspace, the suite
whose flat groceries the plane constant mis-places by ~8cm — goes from a **−3.5pp
inversion to +2.6pp**, and its grasp rate more than doubles (15.8%→36.8%
`grasped_correct`). Goal collapses from +18.4pp to +3.5pp.

The Goal mechanism is `z_place`, not `z_pick`, and it is specific to
**region-typed destinations**. When the arrow head points at an object, depth
reads that object's surface and behaves. When it points at a *region* — an empty
patch of table — there is no object surface at that pixel, so the ray reads
whatever lies behind it, sometimes the floor well below the table:

| Goal target → destination | n | plane ✓ | depth ✓ | median `z_place` (depth) |
|---|---|---|---|---|
| `akita_black_bowl` → OBJECT | 14 | 10 | 6 | 0.9124 |
| `akita_black_bowl` → REGION | 5 | 3 | 1 | 0.9476 |
| `cream_cheese` → OBJECT | 13 | 0 | 0 | 0.9123 |
| `plate` → REGION | 2 | 0 | 0 | 0.9044 |
| `wine_bottle` → REGION | 4 | 0 | 0 | **0.7068** |

Under the plane route `z_place` is 0.92 everywhere. `wine_bottle → REGION` reads
**0.707** — over 20cm below the table, i.e. the far floor — so the release drives
into the tabletop. **Depth is trustworthy only where the pixel lands on an
object**; a region destination has nothing to land on. This is the honest cost of
the upper bound and the reason the plane route stays the default.

### The control tiers were not a pure kinematic ceiling

Control-tier `auto` success, which bounds what the scripted executor can do at
all:

| suite | plane | depth |
|---|---|---|
| spatial | 80% | **100%** |
| object | 40% | **60%** |
| goal | 40% | **20%** |

Spatial's ceiling was never 80% — it is 100% once the pick point is placed
accurately, and Object's was 40% only because of the mis-placed plane constant.
A meaningful part of what looked like grasp brittleness was deprojection error.
Goal moves the other way, for the region-destination reason above.

### By suite × tier (plane route, the quotable one)

| suite | control | referential | directional | both |
|---|---|---|---|---|
| spatial `text_only`→`auto` | 80%→80% | 19%→67% | 30%→89% | 11%→58% |
| object `text_only`→`auto` | 40%→40% | 6%→0% | 19%→11% | 0%→0% |
| goal `text_only`→`auto` | 40%→40% | 8%→33% | 22%→22% | 8%→42% |

**Control tiers show no gap, as they must** — a control scene has exactly one
candidate, so `text_guess`'s uniform draw is already the right answer and the
sketch adds nothing to disambiguate. Spatial and Goal show the sketch lifting
referential/directional/both, the exact scenes engineered to be unsolvable from
the caption alone.

**Object under the plane route remains the exception**, and the cause is now
measured rather than inferred: the plane constant mis-places its flat groceries
by ~8cm laterally, so the oracle aims truly at the correct object and misses it,
while `text_guess` sometimes lands on a graspable tall bottle instead. Switching
to depth removes most of it (−3.5pp → +2.6pp). The residual is the
grasp-brittleness limitation below.

Stratifying on `grasp_success_flag` (`meta['grasp']['grasp_success']`, 6/38 Goal
scenes `False`): both conditions score exactly 0% on the `False` stratum
(`success_rate_by_condition_x_grasp_success_flag`) — expected, since a scene the
build-time scripted-grasp probe could not lift at all is not one this harness's
single-recipe motion lifts either; `oracle_success` (the teleport oracle) is what
certifies those 6 scenes are solvable in principle, not the scripted grasp.

## Limitations

- **No human data yet.** The `human:*` / `human_consensus` conditions are
  implemented and load-tested against the mechanism (missing-file handling,
  scene scoping) but have never scored a real annotator. This is the natural
  next step once `outputs/human_study/responses/` has files in it.
- **`ScriptedSketchOracle` is a single fixed-recipe grasp, not the builders'
  own multi-try probe.** The builders search `(approach_dz, close_sign) ∈
  {0.005, 0.03} × {-1, +1}` and keep whichever lifts; this harness's motion uses
  ONE combination per scene, read from that scene's own `meta['grasp']`
  (`close_sign`, `approach_dz`) when known, so it reuses the mechanically
  correct recipe rather than guessing — this is a property of the object/
  gripper pair, not the sketch's disambiguating identity, so passing it to
  `ScriptedSketchOracle` is not a ground-truth leak. It is still one fixed
  attempt: combined with the auto sketch's intentional ±3px circle-centre jitter
  (the same jitter the human-sketch imprecision study measures against), this
  measurably fails narrow objects the exact-position builder probe succeeds on
  — observed directly on `object/scene_0000` (milk carton): the oracle using the
  jittered auto-sketch centre failed to lift, while the same motion using the
  exact `all_pixels` centre (as `TextOnlyGuessPolicy` sees on a control-tier,
  single-candidate scene) succeeded. This is a real, intended measurement of
  sketch-precision sensitivity, not a bug — but it means the oracle is not
  expected to reach 100%, and its number should be read as "solvable given a
  perfect *reading* of the sketch and one grasp attempt," not "solvable given a
  perfect grasp."
- **`SUPPORT_Z` is one constant per suite**, not per category, and for Object it
  is measurably wrong for part of the suite. Deprojecting each instance's
  recorded `all_pixels` centre at `z=0.065` and comparing against its true
  `meta['placements']` xy — 225 instances across all 38 Object scenes — gives:

  | category | best-fit z | lateral error @ 0.065 |
  |---|---|---|
  | `basket`, `milk`, `orange_juice`, `salad_dressing`, `ketchup` | 0.060–0.066 | 1.0–1.6 cm |
  | `tomato_sauce`, `alphabet_soup`, `bbq_sauce` | 0.040–0.046 | 3.0–4.1 cm |
  | `chocolate_pudding` | 0.016 | 7.5 cm |
  | `butter`, `cream_cheese` | 0.010 | 8.1–8.2 cm |

  The constant was fitted to the tall groceries. Visual-centre height actually
  spans 0.010–0.066 m, and **5.6 cm of z error becomes ~8 cm of *lateral* error**
  at this camera angle. The earlier claim that `HOVER_DZ`/`APPROACH_DZ` absorb it
  was wrong: those absorb error along z, and this manifests in xy. The three
  worst categories appear **only in the non-control Object tiers**, which is why
  Object's control tier ties between conditions while every other tier does not.

  **A per-category table is not the fix.** Category identity is ground truth —
  the same leak class as the nearest-instance snap deliberately excluded from
  the sketch path — and Goal metas carry no `placements` to validate such a
  table against. `--deproject depth` is the fix: it reads true z at whatever
  pixel the policy chose, needs no category label, and is honestly labelled an
  upper bound. Measured against the same 225 instances, depth cuts the flat-box
  error from 7.94 cm to 2.61 cm, at the cost of being slightly worse on tall
  objects (4.30 cm vs 3.63 cm overall) because it returns the *visible top
  surface*, which is laterally offset from the base centroid at this angle.
- **The wrong-destination attribution is an xy-proximity proxy**
  (`WRONG_DEST_APPROX_TH = 0.08m`), not LIBERO's true `check_contact`/
  `check_ontop`/`in_box` logic. It is never used for the reported success
  number, only for the `nearest_destination` / `correct_destination`
  failure-attribution columns.
- **The depth route is an upper bound and must always be reported as one.** It
  reads true rendered z at the chosen pixel; a real RGB-only policy has no depth
  channel. `run_config.json` and `summary.json` both carry `upper_bound: true`
  with a reason string, and every `results.csv` row carries its own `deproject`
  column, so a depth run can never be mistaken for a plane run after the fact.
  The plane route remains the non-privileged default and the number to quote
  when only one is quoted.
- **Depth is only valid where the pixel lands on an object.** A region-typed
  destination has no surface at the arrow head, so the ray reads whatever is
  behind it — measured at `z_place = 0.707` on Goal's `wine_bottle → REGION`
  scenes, over 20cm below the table. This is why depth *lowers* Goal from
  +18.4pp to +3.5pp while raising Object from −3.5pp to +2.6pp. A robust
  version would fall back to the suite constant when the depth sample is
  implausible for the suite (e.g. more than a few cm below the support plane);
  that check is not implemented.
- **The scripted policies are the proof-of-loop, not the finding.** The
  project's actual open item — a learned (UniVLA) policy compared against these
  baselines on a GPU — is unchanged by this harness; `Prompt` /
  `SketchPolicy` are the seam it plugs into (`sketch_policies.py`,
  numpy-only, no simulator import).
